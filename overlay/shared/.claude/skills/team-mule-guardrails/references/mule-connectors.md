# Mule connector and scope rules

Reference for [the Mule XML rules](../../../rules/mule-xml.md). Read it when the flow uses SFTP, Anypoint MQ, Batch, Salesforce, VM queues or the Cache scope. Links are examples; use documentation for the project's connector versions.

- SFTP sources: before enabling auto-delete or move, decide whether failed files must remain for retry. The SFTP 2.4 source defaults **Apply Post Action When Failed** to `true`; set it to `false` when failed files must remain, and preserve the failure to the source. Check the project's connector version and watermark/redelivery strategy together; retaining a file alone does not establish that it will be selected again. See [SFTP source reference](https://docs.mulesoft.com/sftp-connector/latest/sftp-documentation#listener).
- Anypoint MQ subscribers: keep acknowledgement tied to successful processing. `AUTO` acknowledges when the flow completes successfully; an error handled with `on-error-continue` can therefore acknowledge failed business work. Work handed to Async is not complete merely because the subscriber flow succeeded. `MANUAL` lets the flow decide; `IMMEDIATE` acknowledges on receipt, so a later failure loses the message. Allow enough acknowledgement time for processing and delays (two minutes when unset), and tolerate redelivery if it expires. Use separate queues per environment and developer. See [Anypoint MQ acknowledgement](https://docs.mulesoft.com/anypoint-mq-connector/4.x/anypoint-mq-ack), [error ownership](https://docs.mulesoft.com/mule-runtime/4.9/on-error-scope-concept) and [Async](https://docs.mulesoft.com/mule-runtime/4.9/async-scope-reference).
- In MQ `MANUAL` mode, save `attributes.ackToken` before another operation replaces the message attributes. When Consume uses a target, include the attributes with `targetValue="#[message]"` if the token is needed, and ACK/NACK using the saved token. See [manual acknowledgement](https://docs.mulesoft.com/anypoint-mq-connector/4.x/anypoint-mq-ack).
- Batch jobs: records are processed in blocks (`blockSize` default 100, `maxConcurrency` default twice the cores); use a Batch Aggregator for bulk writes, and consider For Each for small record sets. Record failures are governed by `maxFailedRecords` (default 0 stops the job instance at the first failed record) and each step's `acceptPolicy`/`acceptExpression`, not by the surrounding flow's `on-error-*` handlers. See [batch reference](https://docs.mulesoft.com/mule-runtime/4.9/batch-reference).
- Salesforce writes can return normally with failed records. Inspect the pinned operation's aggregate and per-record results before reporting success or acknowledging upstream work. For Bulk API jobs, retain job/batch IDs and check final status and failed/unprocessed results, or follow an explicit asynchronous acceptance contract. Do not blindly replay already successful records. See [Salesforce results and Bulk operations](https://docs.mulesoft.com/salesforce-connector/latest/salesforce-connector-reference) and the Batch reference above.
- VM queues connect flows within an application and, through shared configuration, separate applications in the same Mule domain. They do not connect separately deployed CloudHub applications. On standalone runtimes the queue type defaults to `TRANSIENT`; `PERSISTENT` serializes messages to disk (or to the memory grid in a cluster). See [VM connector](https://docs.mulesoft.com/vm-connector/latest/). On CloudHub 1.0, messages survive a restart only if Persistent Queues is enabled for the application; it adds tens of milliseconds per message and does not guarantee one-time delivery, so consumers must tolerate duplicates. See [persistent queues](https://docs.mulesoft.com/cloudhub-1/managing-queues).
- Cache scope: by default the cache key is a SHA-256 hash of the payload, so when the result depends on attributes, variables or the caller's identity, define the key in a caching strategy. Only repeatable streams are cached. Cache only data that changes rarely, use a configured object store with an expiry, invalidate entries when the source changes, and never let one caller's data be served to another. See [Cache scope](https://docs.mulesoft.com/mule-runtime/4.9/cache-scope).
